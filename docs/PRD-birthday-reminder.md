# PRD: 生日提醒 App（农历/公历）

| 字段 | 值 |

| 目标平台 | iOS + Android |

## Problem Statement

用户的家人和朋友分布在农历和公历两种历法体系过生日。农历生日每年对应的公历日期都不同，且存在闰月等特殊情况，靠记忆或手工换算极易遗漏和记错。用户希望有一个工具，能够统一管理所有亲友的生日（无论农历还是公历），并自动计算下一次生日的日期、提前推送提醒，让自己再也不错过任何一位亲友的生日。

## Solution

一款本地优先的移动 App（Flutter，一套代码同时支持 iOS 和 Android）：

- 用户录入亲友的姓名、关系和生日，录入时自由选择「农历」或「公历」，并标注是否过闰月生日、是否按虚岁显示年龄。
- App 内置历法引擎，自动完成农历与公历的相互转换（含闰月），为每位联系人持续计算「下一次生日」及倒计时天数。
- 按临近程度排序展示生日列表，当天寿星置顶高亮。
- 到达用户设定的提前天数时发送本地通知提醒；当天再次提醒。
- 全部数据存储在本机，支持导出/导入 JSON 文件做备份与迁移。

## User Stories

### 联系人与生日录入

1. 作为 App 用户，我想添加一位联系人并填写姓名，以便识别是谁的生日。
2. 作为 App 用户，我想为联系人选择「农历」或「公历」作为生日类型，以便正确计算生日日期。
3. 作为 App 用户，我想录入农历生日的月份、日期（含闰月选项），以便 App 每年自动换算成公历。
4. 作为 App 用户，我想录入公历生日的月份、日期，以便 App 每年重复计算。
5. 作为 App 用户，我想为联系人标注关系（家人/朋友/同事/自定义），以便在列表中分组查看。
6. 作为 App 用户，我想为联系人填写备注（如喜欢的礼物、联系方式），以便生日前做好准备。
7. 作为 App 用户，我想为联系人设置头像，以便更直观地浏览列表。
8. 作为 App 用户，我想选择知道出生年份，以便查看联系人满多少岁。
9. 作为 App 用户，我想在不知道出生年份时只填月日，以便仍然获得生日提醒而不显示年龄。
10. 作为 App 用户，我想编辑已有联系人的信息，以便信息变化时随时修正。
11. 作为 App 用户，我想删除联系人，以便清理不再需要的记录。
12. 作为 App 用户，我想删除前获得确认提示，以免误删数据。
13. 作为 App 用户，我想搜索联系人姓名，以便在联系人较多时快速定位。
14. 作为 App 用户，我想按关系分组筛选生日列表，以便只关注某一类人。

### 历法引擎

15. 作为 App 用户，我想让农历生日自动换算为今年对应的公历日期，以便直观看到还有多少天。
16. 作为 App 用户，我想让农历生日自动滚动到下一年，以便今年的生日过了之后倒计时自动指向明年。
17. 作为 App 用户，我想为闰月出生的联系人选择「按闰月过」或「按平月过」，以便符合其真实习惯。
18. 作为 App 用户，我想让农历腊月三十生日在只有腊月廿九的年份自动落到腊月廿九（除夕），以便不会漏掉提醒。
19. 作为 App 用户，我想让公历 2 月 29 日生日在平年自动落到 2 月 28 日，以便每年都有提醒。
20. 作为 App 用户，我想在联系人详情中同时看到农历和公历两种日期，以便对照确认。
21. 作为 App 用户，我想看到联系人的周岁（可选虚岁）年龄，以便准备寿数相关的礼节。

### 提醒与通知

22. 作为 App 用户，我想为每位联系人单独设置提前提醒天数（如提前 1/3/7/15 天，可多选），以便有足够时间准备。
23. 作为 App 用户，我想在生日当天收到提醒，以便当面送上祝福。
24. 作为 App 用户，我想设置一个全局默认提醒规则，以便新建联系人时自动套用。
25. 作为 App 用户，我想关闭某个联系人的提醒而不删除记录，以便灵活控制打扰。
26. 作为 App 用户，我想在点击通知后直接跳转到对应联系人详情，以便快速查看信息。
27. 作为 App 用户，我想在提醒通知中看到「某某还有 3 天生日」这样的具体文案，以便一眼明白事由。
28. 作为 App 用户，我想在设备重启后提醒依然有效，以便不因重启而漏掉提醒。
29. 作为 App 用户，我想在系统授予/拒绝通知权限时有明确引导，以便理解为什么没收到提醒。
30. 作为 App 用户，我想看到每个联系人「下一次提醒时间」，以便确认提醒已安排。

### 展示与仪表盘

31. 作为 App 用户，我想打开 App 就看到按倒计时天数升序的生日列表，以便最先关注最近的生日。
32. 作为 App 用户，我想让今天过生日的联系人置顶并高亮显示，以便第一时间送上祝福。
33. 作为 App 用户，我想看到每个联系人卡片上的倒计时（如「还有 5 天」「今天」「已过 3 天」），以便快速掌握紧迫程度。
34. 作为 App 用户，我想按月份浏览生日分布，以便了解全年的生日节奏。
35. 作为 App 用户，我想看到统计概览（本月寿星数、今年已过/未过生日数），以便整体把握。

### 数据与备份

36. 作为 App 用户，我想把全部数据导出为 JSON 文件，以便备份或迁移到新手机。
37. 作为 App 用户，我想从 JSON 文件导入数据，以便恢复备份。
38. 作为 App 用户，我想在导入时选择合并或覆盖，以便灵活处理与现有数据的关系。
39. 作为 App 用户，我想卸载重装 App 后通过导入恢复数据，以便数据不丢失。

### 设置

40. 作为 App 用户，我想设置默认历法类型（农历/公历），以便录入时减少一次选择。
41. 作为 App 用户，我想选择年龄显示方式（周岁/虚岁/不显示），以便符合个人习惯。
42. 作为 App 用户，我想设置提醒的默认时刻（如当天早上 9 点），以便提醒在合适的时间到达。
43. 作为 App 用户，我想使用深色模式（跟随系统），以便夜间查看不刺眼。

## Implementation Decisions

### 架构与技术选型

- Flutter + Dart，一套代码覆盖 iOS 与 Android。
- 状态管理使用 Riverpod；分层为 UI 层 → 领域层 → 基础设施层，依赖单向向下。
- 本地数据库使用 SQLite（经 drift 访问），drift 提供类型安全的查询，且支持在测试中用内存数据库。
- 农历/公历转换使用成熟的 Dart 历法库（如 `lunar`），不自行实现天文算法；历法引擎模块对其做薄封装，对外暴露稳定接口。
- 本地通知使用 `flutter_local_notifications`；跨重启的提醒可靠性由「应用启动/数据变更时重新调度全部提醒」的幂等策略保证，配合精确闹钟权限（Android 12+）。
- 文件备份通过系统分享/文件选择器（`file_picker`）读写 JSON。

### 模块划分（6 个模块，均为新建）

1. **历法引擎（CalendarEngine）— 核心深模块**
   - 简单接口、深实现：输入一个「生日规格」与参照日期，输出下一次发生日期、倒计时天数、当年年龄。
   - 接口（概念签名）：
     ```
     enum CalendarType { lunar, solar }
     class BirthdaySpec { CalendarType type; int month; int day; bool leapMonth; bool preferLeap; int? birthYear; }
     class Occurrence { DateTime date; int daysUntil; int? age; bool isToday; }
     Occurrence nextOccurrence(BirthdaySpec spec, DateTime from);
     List<(DateTime solar, String lunarLabel)> monthOverview(int year, int month);
     ```
   - 封装全部难点：农历⇄公历转换、闰月、腊月无三十、2 月 29 日平年回退、跨年滚动。
   - 不依赖数据库、不依赖通知，纯函数式，可完全隔离测试。

2. **联系人档案（PersonRepository）**
   - 负责 Person 实体的增删改查与搜索/筛选。
   - Schema：`persons(id, name, relationship, note, avatarPath, calendarType, month, day, leapMonth, preferLeap, birthYear, reminderOffsetsJson, reminderEnabled, createdAt, updatedAt)`。
   - 生日以「月/日 + 历法类型」存储（而非具体公历日期），公历日期永远由历法引擎现场计算，避免跨年失效。

3. **提醒调度（ReminderScheduler）**
   - 接口：`rescheduleAll(List<Person> persons)`、`cancelAll()`。
   - 根据历法引擎计算的下次生日与用户设置的提前天数，为每个 (联系人 × 提前天数) 组合注册一条本地通知，文案模板「{姓名} 还有 {n} 天生日（{日期}）」。
   - 幂等：每次调用先取消旧计划再重建；App 启动、数据变更、历法表更新时触发。

4. **本地存储（Database + BackupService）**
   - drift 数据库与 DAO；首次启动建表与种子（空）。
   - BackupService：导出为带版本号的 JSON（含 schemaVersion），导入时做版本兼容校验、合并（按内容去重）或覆盖两种策略。

5. **展示层（Dashboard UI）**
   - 生日列表页（按 daysUntil 升序，今日寿星置顶高亮）、联系人编辑页、联系人详情页（双历法对照）、月份总览页、设置页。
   - UI 仅消费历法引擎与仓储的输出，不含任何历法换算逻辑。

6. **设置（SettingsRepository）**
   - 持久化：默认历法、默认提前提醒天数、默认提醒时刻、年龄显示方式（周岁/虚岁/不显示）、主题模式。
   - 以 KV 形式存储，供编辑页与调度器读取默认值。

### 关键交互决策

- 新建联系人：填姓名 → 选历法 → 选月/日（农历含闰月开关与「无则回退」策略开关）→ 可选关系/备注/年份 → 保存。
- 通知权限被拒时，在设置页与列表页顶部展示持久提示条并引导到系统设置。
- 「今天」的判定以设备本地时区为准。
- 生日规格变更、导入数据后必须触发 `ReminderScheduler.rescheduleAll`。

## Testing Decisions

### 测试原则

- 只测模块的外部行为（给定输入 → 期望输出），不测内部实现细节。
- 历法引擎是最高风险区域（闰月、无大年三十、2 月 29、跨年滚动），必须有穷举式已知用例表。
- 所有时间相关测试注入假时钟/假参照日期，不依赖真实"今天"。

### 各模块测试

1. **历法引擎（单元测试，重点）**
   - 已知农历公历对照表用例（如 2025 乙巳年闰六月等权威对照）。
   - 边界：腊月三十缺失年份回退到廿九；闰月生日的两种策略；2 月 29 平年回退；生日当天 daysUntil == 0 且 isToday；12 月底生日跨年滚动到次年。
   - 无状态纯函数，直接断言输入输出。
2. **联系人档案（仓储测试，drift 内存库）**
   - 增删改查、搜索、按关系筛选、删除确认属于 UI 层行为（widget 测试覆盖）。
3. **提醒调度（单元测试 + fake 通知插件）**
   - 断言注册的通知数量 = 有效联系人 × 提前天数组合；文案正确；reminderEnabled=false 不注册；幂等（重复调用不产生重复计划）。
4. **备份服务（单元测试）**
   - 导出→导入往返数据一致；版本不兼容被拒绝；合并策略去重、覆盖策略清空后写入。
5. **设置（仓储测试）**
   - 默认值读写、枚举序列化往返。
6. **Dashboard UI（widget 测试）**
   - 注入固定假数据：今日寿星置顶高亮、按 daysUntil 升序、倒计时文案（「今天/还有 N 天/已过 N 天」）渲染正确。

## Out of Scope

- 云端同步与账号体系（多设备同步、登录注册）。
- 自动发送生日祝福短信/微信。
- 桌面小组件（iOS Widget / Android Widget）与手表应用。
- 礼物推荐、愿望清单等增值功能。
- 联系人头像拍照/图片编辑（仅支持从相册选取）。
- 多语言（首版仅简体中文）。
- 农历之外的历法体系（伊斯兰历、佛历等）。

## Further Notes

- 数据完全本地化，无网络请求，天然规避隐私合规问题；备份 JSON 由用户自行保管。
- 农历换算依赖历法库的对照表数据（通常覆盖 1900–2100 年），超出范围的老人生日需在录入时给出校验提示。
- 后续可演进方向（本版不做）：年度生日统计图表、iCloud/网盘备份集成、小组件。
